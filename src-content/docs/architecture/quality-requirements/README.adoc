== Detaillierte Qualitätskriterien

=== 🎯 Reproduzierbarkeit

*Dokument:* <<reproducibility.adoc,Reproduzierbarkeit>>

[cols="1,3,1", options="header"]
|=== 
|ID |Beschreibung |Messkriterium 

|QA-REP-001 
|Gleiche Input-Dateien und Umgebung führen zu identischen Output-Dateien. 
|Build-Hash Prüfsumme stimmt bei wiederholten Läufen überein 

|QA-REP-002 
|Build-Ergebnisse sind unabhängig von der Host-Umgebung (Betriebssystem, installierte Tools). 
|Build in Docker-Container und lokal (mit gleichem Image) produziert identische Ergebnisse 

|QA-REP-003 
|Versionierte Docker-Images ermöglichen deterministische Builds. 
|Image-Tags sind unveränderlich (immutable) 

|===

* <<../05-building-blocks,Baustein Docker-Image>>
* <<../decisions/ADR-003-use-docker.adoc,ADR-003: Use Docker for reproducibility>>

=== 🛠️ Wartbarkeit

*Dokument:* <<maintainability.adoc,Wartbarkeit>>

[cols="1,3,1", options="header"]
|=== 
|ID |Beschreibung |Messkriterium 

|QA-MNT-001 
|Klare Trennung von Content, Präsentation und Build-Logik (Separation of Concerns). 
|Jede Datei hat einen klaren Verantwortungsbereich 

|QA-MNT-002 
|Modulare Gradle-Tasks ermöglichen einfache Änderungen und Erweiterungen. 
|Neue Output-Formate können durch Hinzufügen eines Tasks unterstützt werden 

|QA-MNT-003 
|Dokumentation der Architekturentscheidungen (ADRs) für nachvollziehbare Entscheidungen. 
|Jede signifikante Entscheidung ist als ADR dokumentiert 

|QA-MNT-004 
|Verwendung von Standards und Best Practices (AsciiDoc, Gradle, arc42). 
|Einhaltung etablierter Konventionen 

|QA-MNT-005 
|Automatisierte Validierung der Dokumentationsstruktur. 
|CI-Pipeline prüft auf gebrochene Links, fehlerhafte Includes 

|===

=== 🤖 Automatisierbarkeit

*Dokument:* <<automability.adoc,Automatisierbarkeit>>

[cols="1,3,1", options="header"]
|=== 
|ID |Beschreibung |Messkriterium 

|QA-AUT-001 
|100% der Build- und Deployment-Prozesse sind automatisiert. 
|Keine manuellen Schritte im Normalbetrieb nötig 

|QA-AUT-002 
|CI/CD-Pipeline führt alle Builds und Deployments aus. 
|Push zu main löst automatisch Build und Deployment aus 

|QA-AUT-003 
|Lokale Entwicklungsumgebung unterstützt die gleichen Kommandos wie CI. 
|`./build.sh` und `./gradlew` funktionieren lokal und in CI 

|QA-AUT-004 
|Fehler in der Pipeline führen zu klaren Fehlermeldungen. 
|Jeder Fehler hat eine verständliche Meldung und Logs 

|===

=== ⚡ Performance

*Dokument:* <<performance.adoc,Performance>>

[cols="1,3,1", options="header"]
|=== 
|ID |Beschreibung |Messkriterium 

|QA-PERF-001 
|Build-Dauer für lokale Entwicklung < 2 Minuten. 
|Gemessen mit `time ./gradlew buildAll` 

|QA-PERF-002 
|Build-Dauer in CI/CD < 5 Minuten. 
|Gemessen über GitHub Actions Logs 

|QA-PERF-003 
|Change Detection reduziert unnötige Builds. 
|Builds werden nur bei relevanten Änderungen ausgeführt 

|QA-PERF-004 
|Gradle nutzt Caching für Abhängigkeiten. 
|`.gradle`-Verzeichnis wird zwischen Builds gecached 

|QA-PERF-005 
|Website-Ladezeit < 2 Sekunden (First Contentful Paint). 
|Gemessen mit Lighthouse oder WebPageTest 

|===

=== 🔒 Sicherheit

*Dokument:* <<security.adoc,Sicherheit>>

[cols="1,3,1", options="header"]
|=== 
|ID |Beschreibung |Messkriterium 

|QA-SEC-001 
|Keine Secrets oder privaten Daten im Repository. 
|`.gitignore` blockiert `.env` und sensitive Dateien 

|QA-SEC-002 
|Sichere Speicherung von Secrets in GitHub Secrets. 
|Keine Secrets in Plaintext in Dateien 

|QA-SEC-003 
|Sichere Authentifizierung für Deployment (SFTP, Git API). 
|Tokens/Passwörter werden sicher übertragen 

|QA-SEC-004 
|Keine Injection-Angriffe durch Benutzereingaben. 
|AsciiDoc-Inhalte werden nicht direkt in HTML eingebettet 

|QA-SEC-005 
|Regelmäßige Updates der Abhängigkeiten. 
|Dependencies werden monatlich geprüft 

|===
