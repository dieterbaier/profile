== Detaillierte Stakeholder-Analyse

=== ST-001: Dieter Baier (Autor)

[cols="1,2", options="header"]
|=== 
|Aspekt |Beschreibung 

|**Rolle** 
|Primärer Nutzer und Entwickler des Systems 

|**Ziele** 
|- **Effizienz:** Minimaler Aufwand für Pflege der Profile  
- **Qualität:** Hohe Qualität der generierten Dokumente  
- **Flexibilität:** Einfache Anpassung an neue Anforderungen  
- **Lernbereitschaft:** Nutzung moderner Technologien (AsciiDoc, Gradle, Docker) 

|**Erwartungen** 
|- Einfache Bedienung (z. B. `./build.sh buildAll`)  
- Schnelle Build-Zeiten  
- Klare Fehlerbedingungen  
- Gute Dokumentation 

|**Befürchtungen** 
|- Zu hohe Komplexität  
- Wartungsaufwand für Docker-Images  
- Abhängigkeit von externen Tools 

|**Einfluss auf Architektur** 
|- Wahl von AsciiDoc als Format (vertraut mit Markup-Sprachen)  
- Entscheidung für Gradle (Erfahrung mit Java-Build-Tools)  
- Fokus auf Automatisierung (CI/CD-Erfahrung) 

|**Verweise** 
|- siehe <<01-vision-and-goals,Vision & Ziele>> (primärer Nutzer der Ziele)  
- siehe <<05-building-blocks,Bausteine>> (alle Komponenten werden von ihm genutzt)  
- siehe <<decisions/ADR-001-use-asciidoc.adoc,ADR-001>> (seine Entscheidung für AsciiDoc)  
|=== 

=== ST-002 & ST-003: Arbeitgeber & Kunden

[cols="1,2", options="header"]
|=== 
|Aspekt |Beschreibung 

|**Rolle** 
|Externe Nutzer der generierten Outputs (CV, Website) 

|**Ziele** 
|- Aktuelle und korrekte Informationen  
- Professionelle Darstellung  
- Einfacher Zugriff (Website, PDF-Download) 

|**Erwartungen** 
|- Konsistente Inhalte über alle Kanäle  
- Schnelle Ladezeiten der Website  
- Druckfreundliche PDFs 

|**Befürchtungen** 
|- Veraltete Informationen  
- Gebrochene Links  
- Schlechte Lesbarkeit 

|**Einfluss auf Architektur** 
|- Entscheidung für **mehrere Output-Formate** (HTML, PDF)  
- Fokus auf **Qualität der Präsentation** (Themes)  
- **Separation of Concerns** (Inhalt ≠ Präsentation) für einfache Anpassungen 

|**Verweise** 
|- siehe <<07-quality-requirements,Qualitätsanforderungen>> (Benutzerfreundlichkeit, Korrektheit)  
- siehe <<05-building-blocks,Bausteine>> (Themes für Präsentation)  
|=== 

=== ST-004: Community (GitHub/GitLab)

[cols="1,2", options="header"]
|=== 
|Aspekt |Beschreibung 

|**Rolle** 
|Leser der README-Dateien auf GitHub und GitLab 

|**Ziele** 
|- Klare Information über das Profil  
- Einfache Navigation zu relevanten Ressourcen  
- Transparenz über Aktivitäten 

|**Erwartungen** 
|- Kurze, prägnante READMEs  
- Aktuelle Links  
- Konsistente Informationen 

|**Befürchtungen** 
|- Zu lange READMEs  
- Veraltete Informationen  
- Unklare Struktur 

|**Einfluss auf Architektur** 
|- **Multi-Output** (Markdown für READMEs und Artikel-Exporte)  
- **Automatisiertes Deployment** zu GitHub/GitLab  
- **Inhaltsfilterung** (nur öffentliche Infos in READMEs) 

|**Verweise** 
|- siehe <<04-solution-strategy,Lösungsstrategie>> (Multi-Output-Strategie)  
- siehe <<decisions/ADR-004-use-pandoc.adoc,ADR-004>> (Pandoc für Markdown-Konvertierung)  
|=== 

=== ST-005: GitHub Actions (CI/CD)

[cols="1,2", options="header"]
|=== 
|Aspekt |Beschreibung 

|**Rolle** 
|Ausführende Umgebung für Builds und Deployments 

|**Ziele** 
|- Deterministische Ausführung  
- Ressourcen-Optimierung  
- Zuverlässige Builds 

|**Erwartungen** 
|- Schnelle Build-Zeiten  
- Geringer Speicherbedarf  
- Klare Fehlerbedingungen 

|**Befürchtungen** 
|- Hohe Kosten bei vielen Builds  
- Unvorhersehbares Verhalten  
- Abhängigkeit von GitHub 

|**Einfluss auf Architektur** 
|- **Change Detection** für effiziente Builds  
- **Caching** von Abhängigkeiten (Gradle, Docker-Layers)  
- **Modularisierung** der Build-Tasks 

|**Verweise** 
|- siehe <<04-solution-strategy,Lösungsstrategie>> (Change Detection)  
- siehe <<07-quality-requirements,Qualitätsanforderungen>> (Performance, Reproduzierbarkeit)  
- siehe <<09-risks-and-constraints,Risiken & Constraints>> (GitHub Actions Limits)  
|===
