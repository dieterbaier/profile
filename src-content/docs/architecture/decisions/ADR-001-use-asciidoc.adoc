== Kontext

Maintaining a personal profile across multiple platforms (GitHub, GitLab, personal website, CV) leads to **duplication and inconsistencies**.
Each platform has different requirements for format, length, and content, resulting in:

* **Redundancy:** Same information must be maintained in multiple places
* **Inconsistencies:** Changes are not applied everywhere
* **Error-proneness:** Manual synchronization is prone to mistakes
* **Time consumption:** High maintenance effort for simple updates

We needed a **single source of truth** that could serve as the basis for all outputs, eliminating these problems.

=== Optionen

==== Option 1: AsciiDoc

* **Pros:**
  - Rich markup capabilities (tables, cross-references, includes)
  - Native support for diagrams (PlantUML, Graphviz)
  - Flexible output generation (HTML, PDF, DocBook, Markdown via Pandoc)
  - Strong tooling support (Asciidoctor, Gradle plugins)
  - Used by major documentation projects (e.g., Spring, Eclipse)
  - Mature and actively maintained
  - Supports attributes and conditional content

* **Cons:**
  - Learning curve for new contributors
  - Less widespread than Markdown
  - Requires specific tooling (Asciidoctor)

==== Option 2: Markdown

* **Pros:**
  - Very widespread and familiar
  - Simple syntax for basic use cases
  - Native support on GitHub/GitLab

* **Cons:**
  - Limited features (no native tables, cross-references, includes)
  - No standard for extensions (CommonMark, GFM, etc.)
  - Limited diagram support
  - Less suitable for complex documentation
  - Harder to generate multiple output formats

==== Option 3: reStructuredText (RST)

* **Pros:**
  - Very powerful and feature-rich
  - Native support in Python ecosystem (Sphinx)
  - Good for complex documentation

* **Cons:**
  - Very steep learning curve
  - Less tooling support outside Python ecosystem
  - Verbose syntax
  - Not as widely adopted as Markdown or AsciiDoc

==== Option 4: Custom Format

* **Pros:**
  - Tailored exactly to our needs
  - Maximum flexibility

* **Cons:**
  - High development effort
  - No existing tooling
  - Maintenance burden
  - Not portable

== Entscheidung

We chose **AsciiDoc** as the single source format for all content in this project.

**Pugh Matrix Ergebnis:** AsciiDoc erreicht die höchste gewichtete Punktzahl (+3), gefolgt von RST (+2). Markdown (-1) und Custom (-4) schneiden schlechter ab.

== Konsequenzen

=== Vorteile

Accepted (direct from Pugh analysis)

* Functional Suitability: Single Source of Truth: One AsciiDoc file can generate multiple outputs (HTML, PDF, Markdown)
* Functional Suitability: Rich Features: Support for tables, cross-references, includes, diagrams, and conditional content
* Flexibility: Flexible Output: Can be converted to HTML (Asciidoctor), PDF (Asciidoctor PDF), and Markdown (Pandoc via DocBook)
* Maintainability: Modularity: Includes allow for reusable content components (e.g., projects, contact info)
* Compatibility: Tooling Support: Good integration with Gradle and Docker
* Maintainability: Maturity: Actively maintained with strong community support

=== Nachteile

* Maintainability: Learning Curve: New contributors need to learn AsciiDoc syntax
* Compatibility: Tool Dependency: Requires Asciidoctor and potentially Pandoc
* Maintainability: Less Common: Less widespread than Markdown in some communities

== Alternativen

* **Markdown:** Rejected due to limited features and harder multi-output generation (Pugh: -1)
* **RST:** Rejected due to steep learning curve and limited tooling outside Python (Pugh: +2, but community adoption -1)
* **Custom Format:** Rejected due to high development and maintenance effort (Pugh: -4)
