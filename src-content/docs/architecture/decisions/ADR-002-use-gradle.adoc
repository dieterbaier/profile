== Kontext

With the decision to use <<ADR-001-use-asciidoc.adoc,AsciiDoc as our single source format>>, we needed a **build system** to orchestrate the conversion of AsciiDoc to multiple output formats (HTML, PDF, Markdown).

The build system needs to:

* Coordinate multiple conversion steps (Asciidoctor for HTML/PDF, Pandoc for Markdown)
* Manage dependencies (Asciidoctor plugin, Pandoc, Graphviz)
* Handle different tasks for different outputs (site, CV, README, architecture docs)
* Support both local development and CI/CD environments
* Be extensible for future output formats

Without a proper build system, we would face:

* **Manual processes:** Error-prone, time-consuming
* **Inconsistent builds:** Different results in different environments
* **Poor maintainability:** Hard to extend or modify the build process

=== Optionen

==== Option 1: Gradle

* **Pros:**
  - Strong support for Java-based tools (Asciidoctor Gradle plugin)
  - Excellent dependency management
  - Flexible task definition and orchestration
  - Good IDE support (IntelliJ, Eclipse)
  - Extensible via plugins and custom tasks
  - Strong community and ecosystem
  - Incremental build support
  - Can execute external commands (for Pandoc, Graphviz)

* **Cons:**
  - Java dependency (requires JVM)
  - Learning curve for non-Java developers
  - Verbose configuration (Groovy DSL)
  - Slower startup compared to some alternatives

==== Option 2: Make

* **Pros:**
  - Simple and widely available
  - No language dependencies
  - Good for simple build pipelines
  - Fast execution

* **Cons:**
  - Limited dependency management
  - Less flexible for complex builds
  - No native support for Java-based tools
  - Harder to extend with custom logic
  - No built-in incremental build support
  - Platform-specific issues (Windows vs Unix)

==== Option 3: Maven

* **Pros:**
  - Strong Java ecosystem support
  - Standardized project structure
  - Good dependency management
  - Asciidoctor Maven plugin available

* **Cons:**
  - More rigid and verbose than Gradle
  - Slower than Gradle for incremental builds
  - Less flexible for custom tasks
  - XML configuration is harder to read and write

==== Option 4: Node.js (Gulp/Grunt/Webpack)

* **Pros:**
  - JavaScript ecosystem is widely known
  - Good for web-related tasks
  - Asciidoctor.js available

* **Cons:**
  - No native support for Java-based Asciidoctor
  - Asciidoctor.js has limited features compared to Java version
  - Less mature for documentation build pipelines
  - Additional Node.js dependency

==== Option 5: Shell Scripts

* **Pros:**
  - Simple for basic tasks
  - No additional dependencies
  - Full control over execution

* **Cons:**
  - Hard to maintain for complex builds
  - No dependency management
  - Platform-specific issues
  - Poor error handling
  - No incremental build support

== Entscheidung

We chose **Gradle** as the build system for orchestrating the documentation pipeline.

**Pugh Matrix Ergebnis:** Gradle erreicht die höchste gewichtete Punktzahl (+4), gefolgt von Maven (+2). Make (-3), Node.js (0) und Shell Scripts (-3) schneiden schlechter ab.

== Konsequenzen

=== Vorteile

Accepted (direct from Pugh analysis)

* Maintainability: Rich Plugin Ecosystem: Excellent Asciidoctor Gradle plugin for AsciiDoc processing
* Maintainability: Dependency Management: Built-in support for managing Asciidoctor, Pandoc, and other tool dependencies
* Maintainability: Task Orchestration: Clear definition of build tasks and their dependencies
* Flexibility: Flexibility: Can define custom tasks for specific needs (e.g., Pandoc conversion)
* Flexibility: Extensibility: Easy to add new output formats or build steps
* Maintainability: IDE Support: Good integration with IntelliJ IDEA and other Java IDEs
* Performance: Incremental Builds: Supports incremental builds for better performance
* Portability: Cross-Platform: Works consistently across different operating systems

=== Nachteile

* Compatibility: Java Dependency: Requires Java Runtime Environment (JRE)
* Usability: Learning Curve: Groovy DSL may be unfamiliar to some developers
* Performance: Startup Time: Gradle daemon can have slower startup than some alternatives
* Maintainability: Configuration Complexity: Build scripts can become complex for advanced use cases

== Implementierungsdetails

The Gradle build is configured in `build.gradle` with the following key components:

* **Plugins:** `org.asciidoctor.jvm.convert` and `org.asciidoctor.jvm.pdf` for AsciiDoc processing
* **Custom Tasks:** `PandocTask` and `PandocDirectoryTask` for DocBook to Markdown conversion
* **Configuration:** `asciidoctorBase` function for reusable task configuration
* **Environment Management:** Support for `.env` files and GitHub Secrets

Example task configuration:

```groovy
asciidoctorBase('buildSite','buildCVDownload','src-content/profile/site', 'build/site', [],false, "html5")
```
