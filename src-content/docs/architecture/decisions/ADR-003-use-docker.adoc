== Kontext

A common problem in documentation projects is the **"works on my machine"** issue, where builds succeed on one developer's machine but fail on another's or in CI/CD due to:

* Different tool versions (Asciidoctor, Pandoc, Java, etc.)
* Missing dependencies
* Operating system differences
* Configuration discrepancies

With our decision to use <<ADR-001-use-asciidoc.adoc,AsciiDoc>> and <<ADR-002-use-gradle.adoc,Gradle>>, we needed a way to ensure that:

* All developers have the **same environment**
* The build process is **reproducible** across all machines
* CI/CD pipelines use the **same tools** as local development
* No manual setup is required for new contributors

=== Optionen

==== Option 1: Docker Container

* **Pros:**
  - Complete isolation from host environment
  - Versioned, immutable images
  - Easy to share and distribute
  - Works across all platforms (Linux, macOS, Windows)
  - Good integration with CI/CD (GitHub Actions)
  - Can pre-install all required tools (Asciidoctor, Pandoc, Graphviz, Java)
  - Caching support for faster builds

* **Cons:**
  - Docker installation required on developer machines
  - Image size can be large
  - Slight performance overhead
  - Image maintenance required
  - Learning curve for Docker beginners

==== Option 2: Local Tool Installation Documentation

* **Pros:**
  - No Docker dependency
  - Direct access to host system
  - Better performance

* **Cons:**
  - Manual setup required for each developer
  - Different configurations across machines
  - Hard to ensure version consistency
  - Setup can be complex and error-prone
  - "Works on my machine" problems persist

==== Option 3: Virtual Machines

* **Pros:**
  - Complete environment isolation
  - Can be pre-configured with all tools

* **Cons:**
  - Heavyweight and resource-intensive
  - Slow startup and provisioning
  - Poor integration with CI/CD
  - Harder to version and distribute
  - Platform-specific issues

==== Option 4: Container Alternatives (Podman, LXC)

* **Pros:**
  - Similar benefits to Docker
  - Podman doesn't require daemon

* **Cons:**
  - Less widespread adoption
  - Less mature ecosystem
  - Limited CI/CD integration
  - Less tooling support

==== Option 5: Nix/NixOS

* **Pros:**
  - Declarative environment management
  - Reproducible builds
  - No container overhead

* **Cons:**
  - Very steep learning curve
  - Limited adoption outside functional programming community
  - Complex setup
  - Poor IDE integration

== Entscheidung

We chose **Docker Container** (`docs-toolbox`) as the runtime environment for our documentation builds.

**Pugh Matrix Ergebnis:** Docker (+1) und Podman (0) schneiden am besten ab. Local Installation (-4), VMs (-2) und Nix/NixOS (-2) sind weniger geeignet.

Entscheidung für Docker aufgrund der besseren CI/CD-Integration und Community/Ecosystem trotz leichtem Performance-Overhead und Image-Größe.

== Konsequenzen

=== Vorteile

Accepted (direct from Pugh analysis)

* Reproducibility: Reproducibility: Same Docker image produces identical results on any machine
* Security: Isolation: Complete separation from host environment (tools, versions, OS)
* Portability: Portability: Docker images work on any platform supporting Docker
* Maintainability: Versioning: Images can be tagged and versioned for consistency
* Compatibility: CI/CD Integration: Seamless integration with GitHub Actions
* Maintainability: Pre-configured: All required tools (Asciidoctor, Pandoc, Graphviz, Java) are pre-installed
* Performance: Caching: Docker layer caching improves build performance
* Usability: Zero Setup: No local tool installation required for developers

=== Nachteile

* Compatibility: Docker Dependency: Requires Docker installation on developer machines
* Efficiency: Image Size: Docker images can be large (100s of MB)
* Performance: Performance Overhead: Slight overhead compared to native execution
* Maintainability: Image Maintenance: Docker images need to be updated with new tool versions
* Usability: Learning Curve: Docker knowledge required for advanced use cases

== Alternativen

* **Local Installation:** Rejected due to reproducibility issues (Pugh: -4)
* **Virtual Machines:** Rejected due to resource overhead and poor CI/CD integration (Pugh: -2)
* **Container Alternatives:** Rejected due to limited ecosystem and CI/CD integration (Pugh: 0)
* **Nix/NixOS:** Rejected due to complexity and learning curve (Pugh: -2)

== Implementierungsdetails

The Docker setup consists of:

* **Base Image:** `eclipse-temurin:17` (official Java image)
* **Tools Installed:**
  - Asciidoctor (via RubyGem)
  - Pandoc
  - Graphviz
  - Git
  - Other CLI utilities
* **Image Registry:** GitHub Container Registry (GHCR)
* **Image Tag:** `ghcr.io/docs-as-code-toolkit/docs-toolbox:v1.1.0`

Example usage:

```bash
# Local development
docker run --rm \
  -v $(pwd):/app \
  -v $HOME/.gradle:/root/.gradle \
  -w /app \
  ghcr.io/docs-as-code-toolkit/docs-toolbox:v1.1.0 \
  ./gradlew buildAll

# GitHub Actions
- name: Run build
  run: |
    docker run --rm \
      -v ${{ github.workspace }}:/app \
      -v $HOME/.gradle:/root/.gradle \
      -w /app \
      ghcr.io/docs-as-code-toolkit/docs-toolbox:v1.1.0 \
      ./gradlew buildAll
```

== Mitigationsstrategien

To address the risks associated with this decision:

* **RISK-001 (Image Maintenance):**
  - Monitor `docs-toolbox` project activity
  - Maintain fork of `docs-toolbox` if original is abandoned
  - Document process for building custom images

* **Performance Overhead:**
  - Use Docker layer caching
  - Minimize image size
  - Cache Gradle dependencies between builds

* **Learning Curve:**
  - Provide Docker setup documentation
  - Include `build.sh` wrapper script for simplicity
