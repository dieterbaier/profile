== Einleitung

Die Prinzipien und Regeln dieses Projekts basieren auf den **Docs-as-Code-Philosophien** von Ralf D. Müller und den **Best Practices** für Softwarearchitektur.
Sie dienen als **Leitfaden für alle Architekturentscheidungen** und helfen, **Konsistenz** und **Wartbarkeit** zu gewährleisten.

== Architekturprinzipien

Die folgenden Prinzipien sind **fundamental** für das Projekt und beeinflussen **alle Entscheidungen**.

=== 1. Docs-as-Code Prinzipien

[cols="1,2,1,1", options="header"]
|=== 
|ID |Prinzip |Beschreibung |Verknüpfungen 

|PR-DCC-001 
|**Dokumentation ist Code** 
|Dokumentation wird wie Sourcecode behandelt: versioniert in Git, Peer-Review, Branch-Schutz. 
|<<07-quality-requirements,Qualitätsanforderung Wartbarkeit>> 

|PR-DCC-002 
|**Single Source of Truth** 
|Es gibt genau eine Quelle für jede Information. Duplikate werden vermieden. 
|<<01-vision-and-goals,Mission Statement>>, <<decisions/ADR-001-use-asciidoc.adoc,ADR-001>> 

|PR-DCC-003 
|**Automatisierung** 
|Alle repetitiven Prozesse (Build, Test, Deploy) werden automatisiert. 
|<<01-vision-and-goals,Sekundäres Ziel Automatisierung>>, <<07-quality-requirements,Qualitätsanforderung Automatisierbarkeit>> 

|PR-DCC-004 
|**Versionierung** 
|Alle Artefakte (Dokumente, Images, Tools) sind versioniert und reproduzierbar. 
|<<07-quality-requirements,Qualitätsanforderung Reproduzierbarkeit>>, <<decisions/ADR-003-use-docker.adoc,ADR-003>> 

|PR-DCC-005 
|**Modularität** 
|Dokumentation und Build-Prozess bestehen aus wiederverwendbaren Bausteinen. 
|<<07-quality-requirements,Qualitätsanforderung Wartbarkeit>>, <<decisions/ADR-002-use-gradle.adoc,ADR-002>> 

|PR-DCC-006 
|**Separation of Concerns** 
|Inhalt, Präsentation und Logik sind strikt getrennt. 
|<<01-vision-and-goals,Mission Statement>>, <<05-building-blocks,Baustein Content>>, <<05-building-blocks,Baustein Themes>>, <<05-building-blocks,Baustein Gradle Build>> 

|===

* Alle <<decisions/README.adoc,ADRs>>
* <<07-quality-requirements,Qualitätsanforderung Wartbarkeit>>
* <<07-quality-requirements,Qualitätsanforderung Automatisierbarkeit>>

=== 2. Software-Architektur Prinzipien

[cols="1,2,1,1", options="header"]
|=== 
|ID |Prinzip |Beschreibung |Verknüpfungen 

|PR-SA-001 
|**KISS (Keep It Simple, Stupid)** 
|Einfache Lösungen sind komplexen vorzuziehen. 
|<<decisions/ADR-005-green-it.adoc,ADR-005>>, <<07-quality-requirements,Qualitätsanforderung Wartbarkeit>> 

|PR-SA-002 
|**DRY (Don't Repeat Yourself)** 
|Wiederholter Code oder Inhalte werden vermieden. 
|<<01-vision-and-goals,Mission Statement>>, <<05-building-blocks,Baustein Content>> (Includes) 

|PR-SA-003 
|**YAGNI (You Aren't Gonna Need It)** 
|Es wird nur das implementiert, was aktuell benötigt wird. 
|<<decisions/ADR-005-green-it.adoc,ADR-005>>, <<07-quality-requirements,Qualitätsanforderung Nachhaltigkeit>> 

|PR-SA-004 
|**Separation of Concerns** 
|Jede Komponente hat genau eine Verantwortung. 
|<<PR-DCC-006,PR-DCC-006>>, <<05-building-blocks,Alle Bausteine>> 

|PR-SA-005 
|**Loose Coupling** 
|Bausteine sind so weit wie möglich entkoppelt. 
|<<06-interfaces,Alle Schnittstellen>>, <<05-building-blocks,Alle Bausteine>> 

|PR-SA-006 
|**High Cohesion** 
|Verwandte Funktionalität ist in einer Komponente gebündelt. 
|<<05-building-blocks,Baustein Gradle Build>>, <<05-building-blocks,Baustein Themes>> 

|===

== Regeln (Konkrete Umsetzung der Prinzipien)

Regeln sind **spezifische, überprüfbare** Vorgaben, die aus den Prinzipien abgeleitet werden.

=== Regeln für Content

[cols="1,2,1,1", options="header"]
|=== 
|ID |Regel |Begründung |Verknüpfungen 

|RU-CNT-001 
|Alle Inhalte müssen in AsciiDoc geschrieben sein. 
|Single Source of Truth 
|<<PR-DCC-002,PR-DCC-002>>, <<decisions/ADR-001-use-asciidoc.adoc,ADR-001>> 

|RU-CNT-002 
|Wiederverwendbare Inhalte müssen als Includes realisiert sein. 
|DRY-Prinzip 
|<<PR-SA-002,PR-SA-002>>, <<05-building-blocks,Baustein Content>> 

|RU-CNT-003 
|Includes müssen relative Pfade verwenden. 
|Portabilität 
|<<PR-DCC-004,PR-DCC-004>>, <<05-building-blocks,Baustein Content>> 

|RU-CNT-004 
|Jede AsciiDoc-Datei muss eine klare Verantwortung haben. 
|Separation of Concerns 
|<<PR-DCC-006,PR-DCC-006>>, <<07-quality-requirements,Qualitätsanforderung Wartbarkeit>> 

|RU-CNT-005 
|Öffentliche und private Inhalte müssen strikt getrennt sein. 
|Sicherheit 
|<<05-building-blocks,Baustein Environment Management>>, <<07-quality-requirements,Qualitätsanforderung Sicherheit>> 

|===

[cols="1,2,1,1", options="header"]
