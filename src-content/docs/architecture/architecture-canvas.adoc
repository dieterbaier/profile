== 1. Vision & Ziele

*siehe <<01-vision-and-goals,detaillierte Dokumentation>>*

[cols="1,2", options="header"]
|=== 
|Aspekt |Beschreibung 

|**Mission Statement** 
|*"Write once, publish everywhere"* – Eine zentrale Quelle (AsciiDoc) für alle Ausgaben (Website, CV, README). 

|**Primäres Ziel** 
|Eliminierung von Redundanz und Inkonsistenzen bei der Pflege persönlicher Profile. 

|**Sekundäre Ziele** 
|- Reproduzierbare Builds (kein "works on my machine")  
- Automatisierte Generierung & Deployment  
- Green IT (Ressourcen-sparende Pipelines) 

|**Erfolgsmetriken** 
|- Anzahl manuell gepflegter Dokumente → **0** (nur AsciiDoc-Quelle)  
- Build-Dauer < 5 Min.  
- 100% Determinismus (gleiche Inputs → gleiche Outputs) 

|**Verweise** 
|- Beeinflusst durch: <<07-quality-requirements,Qualitätsanforderungen>> (Reproduzierbarkeit, Automatisierbarkeit)  
- Grundlage für: <<04-solution-strategy,Lösungsstrategie>>, <<05-building-blocks,Bausteine>>
|===

== 4. Lösungsstrategie

*siehe <<04-solution-strategy,detaillierte Dokumentation>>*

[cols="1,3,1,1", options="header"]
|=== 
|Strategie |Umsetzung |Vorteile |Trade-offs 

|**Single Source** 
|AsciiDoc als zentrale Quelle 
|✅ Keine Duplikate  
✅ Einfache Pflege 
|⚠️ Lernkurve für AsciiDoc 

|**Modularer Build** 
|Gradle mit separaten Tasks (`buildSite`, `buildCVPersonal`, etc.) 
|✅ Selektive Builds  
✅ Wiederverwendbar 
|⚠️ Komplexere Konfiguration 

|**Reproduzierbare Umgebung** 
|Docker-Container (`docs-toolbox`) 
|✅ Gleiche Tools überall  
✅ Kein Setup 
|⚠️ Image-Maintenance 

|**Change Detection** 
|Path-Filter in GitHub Actions 
|✅ Ressourcen-sparend  
✅ Schnelle Builds 
|⚠️ Komplexere Pipeline 

|**Multi-Output** 
|Asciidoctor → HTML/PDF + Pandoc → Markdown 
|✅ Flexibilität 
|⚠️ Mehrere Conversion-Schritte 

|**Verweise** 
|- Beeinflusst von: <<07-quality-requirements,Qualitätsanforderungen>> (Performance, Automatisierbarkeit)  
- Beeinflusst: <<05-building-blocks,Bausteine>> (welche Tools gewählt werden)  
- Beeinflusst: <<06-interfaces,Schnittstellen>> (wie Bausteine kommunizieren)
|===

== 8. Prinzipien & Regeln

*siehe <<08-principles-and-rules,detaillierte Dokumentation>>*

[cols="1,2", options="header"]
|=== 
|Prinzip/Regel |Beschreibung 

|**Docs-as-Code** 
|Dokumentation = Code (Versionierung, Peer-Review, Branch-Schutz) 

|**Single Source of Truth** 
|AsciiDoc als eine Quelle für alle Ausgaben 

|**Separation of Concerns** 
|Inhalt (`src-content/`) ≠ Präsentation (`theme/`) ≠ Logik (`build.gradle`) 

|**Automatisierung** 
|Build, Test, Deploy in CI/CD 

|**Minimalismus** 
|Keine unnötigen Ressourcen oder Abhängigkeiten (ADR-005)

== 9. Risiken & Constraints

*siehe <<09-risks-and-constraints,detaillierte Dokumentation>>*

[cols="1,2,1", options="header"]
|=== 
|Risiko/Constraint |Auswirkung |Mitigation 

|**AsciiDoc-Lernkurve** 
|Neue Mitwirkende müssen AsciiDoc lernen 
|Dokumentation, Templates 

|**Tool-Abhängigkeiten** 
|Pandoc, Graphviz, Java müssen verfügbar sein 
|Docker-Container (`docs-toolbox`) 

|**Docker-Image-Wartung** 
|`docs-toolbox` muss gepflegt werden 
|Versionierung, automatisierte Tests 

|**GitHub Actions Limits** 
|Kosten bei vielen Builds 
|Change Detection, Caching 

|**SFTP-Abhängigkeit** 
|Deployment scheitert bei SFTP-Problemen 
|Fallback-Mechanismen, Monitoring 

|**Propietäre Inhalte** 
|Persönliche Daten (CV) dürfen nicht öffentlich sein 
|Environment-Variablen, `.gitignore` 

|**Performance bei großen Dokumenten** 
|Lange Build-Zeiten 
|Inkrementelle Builds, Caching 

|**Verweise** 
|- Betrifft: <<04-solution-strategy,Lösungsstrategie>> (Trade-offs)  
- Betrifft: <<05-building-blocks,Bausteine>> (Tool-Auswahl)  
- Betrifft: <<06-interfaces,Schnittstellen>> (Abhängigkeiten)
|===
