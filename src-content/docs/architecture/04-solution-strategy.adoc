== Übersicht der Lösungsstrategien

Die Lösungsstrategie des `profile-dieterbaier`-Projekts basiert auf **fünf zentralen Prinzipien**, die gemeinsam die **Docs-as-Code-Philosophie** umsetzen.

== 1. Single Source Strategy

=== Kontext
Die Pflege mehrerer Profile (GitHub, GitLab, Website, CV) führt zu Redundanz und Inkonsistenzen.

=== Lösung
**AsciiDoc als zentrale Single Source of Truth** für alle Inhalte.

* **Eine Quelle** für alle Ausgaben
* **Keine Duplikate** – alle Inhalte werden zentral gepflegt
* **Includes-Mechanismus** für wiederverwendbare Bausteine

=== Umsetzung

[cols="1,2,1", options="header"]
|=== 
|Aspekt |Beschreibung |Technische Basis 

|**Quellformat** 
|Alle Inhalte in AsciiDoc 
|<<decisions/ADR-001-use-asciidoc.adoc,ADR-001>> 

|**Struktur** 
|Modulare Dateiorganisation (`src-content/`) 
|Verzeichnisstruktur 

|**Wiederverwendung** 
|Includes für gemeinsame Inhalte (z. B. Projekte) 
|AsciiDoc `include::`-Direktive 

|=== 

=== Vorteile

* ✅ **Konsistenz:** Alle Ausgaben basieren auf derselben Quelle
* ✅ **Wartbarkeit:** Änderungen nur an einer Stelle nötig
* ✅ **Qualität:** Einmalige Prüfung der Inhalte

=== Trade-offs

* ⚠️ **Lernkurve:** AsciiDoc muss gelernt werden
* ⚠️ **Tool-Abhängigkeit:** Benötigt Asciidoctor

=== Verweise

* Begründet durch: <<01-vision-and-goals#_mission_statement,Mission Statement>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Konsistenz>>
* Implementiert durch: <<05-building-blocks,Baustein Content (AsciiDoc)>>

== 2. Modularer Build-Prozess

=== Kontext
Komplexe Build-Pipelines sind schwer wartbar und fehleranfällig.

=== Lösung
**Gradle als modulares Build-System** mit separaten Tasks für jedes Output-Format.

* **Jeder Task** hat eine klare Verantwortung
* **Tasks können einzeln** oder kombiniert ausgeführt werden
* **Abhängigkeiten zwischen Tasks** sind explizit definiert

=== Umsetzung

[cols="1,2,1", options="header"]
|=== 
|Task |Verantwortung |Abhängigkeiten 

|**`buildReadme`** 
|Generiert READMEs für GitHub/GitLab 
|`buildReadmeDocbook` → `convertDocBookToMarkdown` 

|**`buildArticlesMarkdown`** 
|Generiert Markdown-Exporte der Website-Artikel 
|`buildArticlesDocbook` → `PandocDirectoryTask` 

|**`buildSite`** 
|Generiert die persönliche Website 
|`buildCVSite`, `buildArchitecture` 

|**`buildCVPersonal`** 
|Generiert persönliches CV mit Kontaktdaten 
|– (unabhängig) 

|**`buildArchitecture`** 
|Generiert die Architekturdokumentation 
|– (unabhängig) 

|**`buildAll`** 
|Generiert alle Ausgaben 
|Alle anderen Tasks 

|=== 

=== Vorteile

* ✅ **Flexibilität:** Einzelne Outputs können unabhängig generiert werden
* ✅ **Wartbarkeit:** Klare Trennung der Verantwortlichkeiten
* ✅ **Testbarkeit:** Einzelne Tasks können isoliert getestet werden

=== Trade-offs

* ⚠️ **Komplexität:** Mehrere Tasks müssen koordiniert werden
* ⚠️ **Overhead:** Kleine Änderungen erfordern ggf. mehrere Builds

=== Verweise

* Begründet durch: <<01-vision-and-goals#_sekundäre_ziele,Sekundäres Ziel Wartbarkeit>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Wartbarkeit>>
* Implementiert durch: <<decisions/ADR-002-use-gradle.adoc,ADR-002: Use Gradle>>
* Implementiert durch: <<05-building-blocks,Baustein Gradle Build>>

== 3. Reproduzierbare Build-Umgebung

=== Kontext
"Works on my machine" ist ein häufiges Problem bei Dokumentations-Builds.

=== Lösung
**Docker-Container (`docs-toolbox`)** mit allen benötigten Tools in versionierter Umgebung.

* **Gleiche Tools** in Entwicklung und CI/CD
* **Keine lokale Installation** nötig
* **Versionierte Images** für Determinismus

=== Umsetzung

[cols="1,2,1", options="header"]
|=== 
|Aspekt |Beschreibung |Technische Basis 

|**Docker-Image** 
|`ghcr.io/docs-as-code-toolkit/docs-toolbox:v1.1.0` 
|<<decisions/ADR-003-use-docker.adoc,ADR-003>> 

|**Enthaltene Tools** 
|Asciidoctor, Pandoc, Graphviz, Java 
|Dockerfile 

|**Execution** 
|Lokal: `docker run` / CI: GitHub Actions 
|`build.sh`, `.github/workflows/` 

|=== 

=== Vorteile

* ✅ **Reproduzierbarkeit:** Gleiche Ergebnisse in jeder Umgebung
* ✅ **Einfachheit:** Kein Setup für neue Entwickler
* ✅ **Isolation:** Keine Konflikte mit lokalen Tools

=== Trade-offs

* ⚠️ **Image-Größe:** Docker-Images können groß sein
* ⚠️ **Wartung:** Images müssen gepflegt werden

=== Verweise

* Begründet durch: <<01-vision-and-goals#_sekundäre_ziele,Sekundäres Ziel Reproduzierbarkeit>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Reproduzierbarkeit>>
* Implementiert durch: <<05-building-blocks,Baustein Docker-Image>>
* Betroffen durch: <<09-risks-and-constraints,Constraint Docker-Image-Wartung>>

== 4. Change Detection Strategy

=== Kontext
Vollständige Builds bei jeder Änderung sind ressourcenintensiv.

=== Lösung
**Path-basierte Change Detection** in GitHub Actions für selektive Build-Ausführung.

* **Nur betroffene Tasks** werden ausgeführt
* **Unnötige Builds** werden übersprungen
* **Ressourcen werden gespart** (Green IT)

=== Umsetzung

[cols="1,2,1", options="header"]
|=== 
|Change Type |Betroffene Tasks |Filter 

|**README-Änderungen** 
|`buildReadme` 
|`src-content/profile/**` 

|**Architektur-Änderungen** 
|`buildArchitecture` 
|`src-content/docs/**` 

|**Website-Änderungen** 
|`buildSite`, `buildCVSite` 
|`src-content/profile/**` 

|**Keine relevanten Änderungen** 
|*kein Build* 
|– 

|=== 

=== Vorteile

* ✅ **Effizienz:** Nur notwendige Tasks werden ausgeführt
* ✅ **Green IT:** Geringerer Ressourcenverbrauch
* ✅ **Schnelligkeit:** Schnellere Pipeline-Durchläufe

=== Trade-offs

* ⚠️ **Komplexität:** Filter müssen gepflegt werden
* ⚠️ **Fehleranfällig:** Falsche Filter können zu fehlenden Builds führen

=== Verweise

* Begründet durch: <<01-vision-and-goals#_sekundäre_ziele,Sekundäres Ziel Green IT>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Performance>>
* Dokumentiert in: <<04-solution-strategy/Build_Pipeline_Strategy.adoc,Build Pipeline Strategy>>
* Betroffen durch: <<09-risks-and-constraints,Risiko GitHub Actions Limits>>

== 5. Multi-Output Strategy

=== Kontext
Unterschiedliche Plattformen benötigen unterschiedliche Formate.

=== Lösung
**Asciidoctor + Pandoc** für die Generierung mehrerer Output-Formate aus einer Quelle.

* **Asciidoctor:** HTML, PDF aus AsciiDoc
* **Pandoc:** Markdown aus DocBook (Zwischenformat)
* **Flexible Pipeline:** Neue Formate können einfach hinzugefügt werden

=== Umsetzung

[cols="1,2,1,1", options="header"]
|=== 
|Output |Format |Zweck |Technische Basis 

|**Website** 
|HTML 
|Persönliche Website 
|Asciidoctor HTML5 

|**CV (Online)** 
|HTML 
|Online-CV auf Website 
|Asciidoctor HTML5 

|**CV (Download)** 
|PDF 
|Downloadbares Dokument 
|Asciidoctor PDF 

|**Persönliches CV** 
|PDF 
|Lokale Datei mit Kontaktdaten 
|Asciidoctor PDF 

|**GitHub README** 
|Markdown 
|Profil-README 
|Pandoc (DocBook → Markdown) 

|**GitLab README** 
|Markdown 
|Profil-README 
|Pandoc (DocBook → Markdown) 

|**Architekturdoku** 
|HTML 
|Dokumentation 
|Asciidoctor HTML5 

|=== 

=== Vorteile

* ✅ **Flexibilität:** Unterstützung mehrerer Plattformen
* ✅ **Zukunftssicherheit:** Neue Formate können einfach hinzugefügt werden
* ✅ **Konsistenz:** Alle Formate basieren auf derselben Quelle

=== Trade-offs

* ⚠️ **Komplexität:** Mehrere Conversion-Schritte
* ⚠️ **Performance:** Längere Build-Zeiten

=== Verweise

* Begründet durch: <<01-vision-and-goals#_primäre_ziele,Primäres Ziel Single Source of Truth>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Flexibilität>>
* Implementiert durch: <<decisions/ADR-001-use-asciidoc.adoc,ADR-001>> (AsciiDoc)
* Implementiert durch: <<decisions/ADR-004-use-pandoc.adoc,ADR-004: Use Pandoc>> (Markdown)
* Betroffen durch: <<05-building-blocks,Bausteine Asciidoctor & Pandoc>>

== 6. Automatisierter Build

=== Kontext

Manuelle Build-Prozesse sind fehleranfällig und nicht skalierbar.

=== Lösung

**Vollständig automatisierte CI/CD-Pipeline** mit GitHub Actions für Build und Deployment.

* **Jeder Push** löst automatisch den Build aus
* **Jeder Merge** zu main löst Deployment aus
* **Lokale Parität:** gleiche Kommandos funktionieren lokal und in CI

=== Umsetzung

[cols="1,2,1", options="header"]
|===
|Aspekt |Beschreibung |Technische Basis 

|**Trigger** 
|Push zu main, Pull Request, manuell 
|GitHub Actions Workflows 

|**Build** 
|Automatisierte Generierung aller Formate 
|Docker Container 

|**Deployment** 
|Automatisches Deployment zu GitHub Pages 
|SFTP / Git API 

|**Lokale Ausführung** 
|`./gradlew build` funktioniert identisch 
|Gradle Wrapper 

|===

=== Vorteile

* ✅ **Zuverlässigkeit:** Keine manuellen Fehler
* ✅ **Schnelligkeit:** Sofortige Verfügbarkeit von Änderungen
* ✅ **Konsistenz:** Gleiche Prozesse überall

=== Trade-offs

* ⚠️ **Komplexität:** Pipeline-Konfiguration muss gepflegt werden
* ⚠️ **Kosten:** CI/CD-Ressourcen können teuer sein

=== Verweise

* Begründet durch: <<01-vision-and-goals#_sekundäre_ziele,Sekundäres Ziel Automatisierung>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Automatisierbarkeit>>
* Implementiert durch: <<05-building-blocks,Baustein GitHub Actions>>

== 7. Sichere Umgebung

=== Kontext

Sensible Daten wie Deployment-Tokens müssen vor unbefugtem Zugriff geschützt werden.

=== Lösung

**Secure Secret Management** mit GitHub Secrets und sicherer Authentifizierung.

* **Keine Secrets** im Repository
* **Alle Tokens** in GitHub Secrets gespeichert
* **Sichere Übertragung** (nicht in Plaintext)

=== Umsetzung

[cols="1,2,1", options="header"]
|===
|Aspekt |Beschreibung |Technische Basis 

|**Secret Storage** 
| Deployment-Tokens, API-Keys 
|GitHub Secrets 

|**Authentifizierung** 
|SFTP mit Schlüsselbasierung 
|SSH Keys 

|**Deployment** 
|Sichere Verbindung zu Zielsystemen 
|GitHub Actions Security 

|**Validierung** 
|Automatisierte Secret-Scans 
|CI/CD-Pipeline 

|===

=== Vorteile

* ✅ **Sicherheit:** Schutz vor Datenlecks
* ✅ **Compliance:** Einhaltung von Sicherheitsstandards
* ✅ **Vertrauen:** Stakeholder können auf Sicherheit vertrauen

=== Trade-offs

* ⚠️ **Setup-Aufwand:** Initialer Konfigurationsaufwand
* ⚠️ **Wartung:** Secrets müssen regelmäßig rotiert werden

=== Verweise

* Begründet durch: <<01-vision-and-goals#_sekundäre_ziele,Sekundäres Ziel Automatisierung>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Sicherheit>>
* Implementiert durch: <<05-building-blocks,Baustein Environment Management>>

== 8. Qualitätsvalidierung

=== Kontext

Fehler in der Dokumentation können Vertrauen der Stakeholder zerstören.

=== Lösung

**Automatisierte Validierung** aller Inhalte, Links, Includes und Diagramme.

* **Include-Check:** Alle AsciiDoc-Includes existieren
* **Link-Validation:** Alle Links sind valide
* **Diagramm-Rendering:** Alle PlantUML-Diagramme rendern ohne Fehler

=== Umsetzung

[cols="1,2,1", options="header"]
|===
|Aspekt |Beschreibung |Technische Basis 

|**Include-Validierung** 
|Prüft alle `include::`-Direktiven 
|CI/CD-Pipeline 

|**Link-Validierung** 
|Prüft alle internen und externen Links 
|Link-Checker Tool 

|**Diagramm-Validierung** 
|PlantUML-Diagramme werden vor Build gerendert 
|Asciidoctor PlantUML 

|**Build-Validierung** 
|Build scheitert bei Fehlern 
|Gradle Build 

|===

=== Vorteile

* ✅ **Korrektheit:** Alle Outputs sind technisch korrekt
* ✅ **Vertrauen:** Stakeholder können auf Qualität vertrauen
* ✅ **Früherkennung:** Fehler werden früh erkannt

=== Trade-offs

* ⚠️ **Build-Zeit:** Validierung erhöht Build-Dauer
* ⚠️ **Komplexität:** Validierungslogik muss gepflegt werden

=== Verweise

* Begründet durch: <<01-vision-and-goals#_primäre_ziele,Primäres Ziel Single Source of Truth>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Korrektheit>>
* Implementiert durch: <<05-building-blocks,Baustein Gradle Build>>

== 9. Konsistentes Design

=== Kontext

Unterschiedliche Ausgaben (Website, CV, READMEs) sollten ein einheitliches Erscheinungsbild haben.

=== Lösung

**Modulare Themes und Styles** für konsistente Darstellung über alle Ausgaben.

* **Einheitliche Themes** für Website und Dokumentation
* **Anpassbare Styles** für verschiedene Use Cases
* **Corporate Design** für alle Ausgaben

=== Umsetzung

[cols="1,2,1", options="header"]
|===
|Aspekt |Beschreibung |Technische Basis 

|**Theme-System** 
|Wiederverwendbare CSS/AsciiDoc-Styles 
|Themes-Verzeichnis 

|**CV-Spezifisch** 
|Spezielle Styles für gedruckte CVs 
|PDF-Stylesheets 

|**Website-Spezifisch** 
|Responsive Design für Web 
|HTML/CSS Themes 

|**Umgebungsabhängig** 
|Öffentliche vs. private Inhalte 
|Environment Variables 

|===

=== Vorteile

* ✅ **Benutzerfreundlichkeit:** Konsistente Erfahrung für Nutzer
* ✅ **Wartbarkeit:** Änderungen an Styles wirken sich überall aus
* ✅ **Professionalität:** Einheitliches Erscheinungsbild

=== Trade-offs

* ⚠️ **Komplexität:** Theme-System muss gepflegt werden
* ⚠️ **Flexibilität:** Zu starre Themes können Anpassungen erschweren

=== Verweise

* Begründet durch: <<01-vision-and-goals#_primäre_ziele,Primäres Ziel Single Source of Truth>>
* Unterstützt durch: <<07-quality-requirements,Qualitätsanforderung Benutzerfreundlichkeit>>
* Implementiert durch: <<05-building-blocks,Baustein Themes>>
