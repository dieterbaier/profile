== DOC-06003: Article Comments Runtime

The parts named here are described in xref:comp-007-article-comments[COMP-007].

=== Scenario 1: Read An Article

Reading an article involves the webspace only. The comment block and its script come from the same host as the page, and the script contacts nothing while the page loads. It only completes the comment link with the address of the article, without query and fragment.

=== Scenario 2: Load Comments

The reader asks for the list. Only this click makes the browser contact GitHub, directly and without a token.

[plantuml]
----
@startuml
actor Reader
participant "Article page\n(article-comments.js)" as Page
participant "GitHub API\napi.github.com" as API

Reader -> Page : clicks "Load existing comments"
Page -> API : search issues with labels\nArtikelkommentar and article ID
note right : GitHub receives the reader's\nIP address and the article ID
API --> Page : matching issues
Page -> Page : keep issues carrying both labels
Page --> Reader : linked titles, or "no comments yet"
@enduml
----

A failed request, GitHub's rate limit, incomplete search results, or more than 1000 results show the error wording and enable the button again. The article itself is not affected.

=== Scenario 3: Write A Comment

The link leads away from the website. Everything after it happens on GitHub, and the website is not involved. GitHub receives the prefilled values and the reader's IP address as soon as the link is opened, whether or not the reader submits anything.

[plantuml]
----
@startuml
actor Reader
participant "Article page" as Page
participant "Issue form\ngithub.com" as Form
participant "Labelling workflow" as Workflow
database "Comments repository\nissues and allowlist" as Repo

Reader -> Page : follows the comment link
Page -> Form : new tab, prefilled with\narticle ID, title, and URL
Reader -> Form : signs in, writes the comment,\nacknowledges that it is public
Form -> Repo : creates a public issue
Repo -> Workflow : issue opened or edited
Workflow -> Repo : assign label Artikelkommentar
Workflow -> Repo : read allowlist
alt article ID is on the allowlist
  Workflow -> Repo : assign the article ID label,\nremove other article ID labels
else article ID is malformed or not on the allowlist
  Workflow -> Workflow : run fails, article ID labels unchanged
  note right of Workflow
    new issue: has no article ID label
    edited issue: keeps its previous one
  end note
end
@enduml
----

The script stops before it removes any label, so what a failed run leaves depends on the issue:

* A new issue has no article ID label. It exists and stays public, but no article lists it, because the list searches for both labels.
* An issue already assigned to an article and edited to an invalid or unlisted ID keeps its previous label. It stays listed under the previous article.

An edit that removes the form's headings ends the script before any of this, without a failed run, and also leaves the labels as they are. A failed run shows in the comments repository only, not on the website.

=== Scenario 4: Synchronize The Allowlist

The build derives the allowlist from the articles eligible for the public website. The `deploy-site` job checks out the comments repository with `ARTICLE_COMMENTS_REPO_TOKEN`, commits the allowlist if it changed, and pushes it, before it mirrors the site to the webspace.

The job only runs when the path filter of the site target matches, so both steps are attempted together, but they take effect separately:

* A failed push stops the job before the site is deployed. Allowlist and site both stay as they were.
* A successful push followed by a failed mirror leaves the new allowlist active while the site is still old or only partly updated. Until a later run completes the mirror, a newly listed article can receive comments before its page is online, and a page already taken off the allowlist can stay online while new comments on it get no article ID label.
