== DOC-06002: Site Operations Runtime

=== Status

Introduced with https://github.com/dieterbaier/profile/issues/114[issue #114]. The steps for renewing a credential are kept in `docs/howto/rotate-deployment-credentials.adoc`; these scenarios describe how the system behaves.

The site is static, so operating it means keeping its deployment working. What runs out over time are the credentials the deployment jobs use, see xref:risk-006-credential-expiry[RISK-006].

=== Scenario 1: Check Credentials

The `Check credentials` workflow runs every Monday and on manual dispatch. It has one job per credential, so a failed job names the credential, and it changes nothing at any target.

[plantuml]
----
@startuml
start
:Monday schedule or manual dispatch;
fork
  :GitHub tokens: read expiry date;
  if (Rejected or less than 14 days left?) then (yes)
    #pink:Job fails;
    stop
  else (no)
    :Dry-run push to the target repository;
  endif
fork again
  :GitLab token: dry-run push;
fork again
  :SFTP password: log in and list the remote base;
end fork
if (Any check rejected?) then (yes)
  #pink:Job fails, GitHub notifies the owner;
else (no)
  :All credentials proven;
endif
stop
@enduml
----

A dry-run push asks the server for push access without sending anything, so it proves write access rather than only a valid token.

The expiry warning covers the GitHub tokens only, because GitHub reports their expiry date with every response. Reading it for the GitLab token would need more access than the deployment does, so its expiry stays a calendar entry. The SFTP password has no expiry date.

=== Scenario 2: Renew A Credential

The owner renews the credential at its provider, stores it in `dieterbaier/profile`, and dispatches `Check credentials`. A green run proves the new value immediately.

A green `Build Docs` run proves nothing here: a deployment job only runs when its paths changed, and a skipped job shows as green.

=== Scenario 3: Deployment With An Expired Credential

Each deployment job fails on its own, so the other targets are still deployed:

[cols="2,3", options="header"]
|===
| Expired credential | Effect
| `ARTICLE_COMMENTS_REPO_TOKEN` | `deploy-site` stops before the upload, so the website is not deployed at all.
| `PROFILE_REPO_TOKEN` | The GitHub profile README stays at its old version.
| `GITLAB_TOKEN` | The GitLab profile README stays at its old version.
| `SFTP_PASSWORD` | Neither the website nor the architecture documentation is deployed.
|===

The published site keeps working in every case, because a failed job leaves the deployed files untouched. Reading and writing comments needs no token either. Only the allowlist goes stale, so comments on a newly published article do not get their article label.

After renewing the credential, re-running the failed job finishes the deployment without repeating the targets that succeeded.
