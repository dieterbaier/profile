[[adr-007-source-adjacent-article-summaries]]
== ADR-007: Source-Adjacent Article Summaries

=== Status

Proposed.

This ADR is AI-assisted and must not be treated as accepted architecture truth
until reviewed and accepted by the accountable owner.

=== Decision

We propose to store file-based article summaries directly next to the source
article. Each summary filename uses the article filename stem plus
`_summary_<target>` and the Markdown extension.

These summaries remain source-controlled writing aids. They are excluded from
generated site and article-export targets, and generated public content must not
link to them.

For example:

[source,text]
----
src-content/profile/site/articles/documentation/doc-as-code.adoc
src-content/profile/site/articles/documentation/doc-as-code_summary_linkedin.md
src-content/profile/site/articles/documentation/doc-as-code_summary_substack.md
src-content/profile/site/articles/documentation/doc-as-code_summary_listed-io.md
----

=== Context

The project already treats profile article sources under
`src-content/profile/site/articles` as product source. AI-assisted article
summaries are paste-ready publication aids for LinkedIn, Substack, and
listed.io.

The previous contract placed written summaries under
`build/article-summaries/<article-slug>/`. That made the summaries generated
workspace artifacts rather than source artifacts, so they were easy to lose and
harder to review in Git history.

The current desired practice is to version summaries together with the article
source. This may change later, but the active workflow should make summary
changes visible in ordinary source-control review.

=== Decision Drivers

* Summary drafts should be preserved in Git history.
* Reviewers should see article and summary changes close together.
* Summary drafts should not become public generated content by accident.
* Generated build output should remain separate from authored or curated source.
* The convention should stay simple enough for agents and humans to apply.
* Future relocation should remain possible through a later ADR and contract update.

=== Considered Options

==== Option 1: Source-adjacent summary files

Store each platform summary next to the article with the naming pattern
`<article-slug>_summary_<target>.md`.

==== Option 2: Build-directory summary files

Keep the existing `build/article-summaries/<article-slug>/<target>.md` layout.

==== Option 3: Central source summary directory

Store summaries under a source-controlled directory such as
`src-content/profile/site/article-summaries/<article-slug>/<target>.md`.

=== Consequences

==== Positive

* Summary drafts become visible in Git history and ordinary review diffs.
* Article source and derived publication drafts are easier to inspect together.
* `build/` remains reserved for reproducible generated outputs.
* The build verifies that generated site and article-export outputs do not contain summary files or `_summary_<target>` references.

==== Negative

* Article directories will contain more Markdown files that are not primary article sources.
* Build and publishing tasks must avoid treating `_summary_<target>.md` files as source articles unless explicitly intended.
* The verification task adds another build rule that must be maintained if generated target directories change.

==== Neutral or Follow-Up

* A future ADR may move summaries again if the workflow becomes fully generated, platform-specific, or automated.
* Validators may later add checks for expected summary targets and naming.

=== Assumptions

* Summary files are curated AI-assisted writing aids, not deterministic build artifacts.
* The source-adjacent naming convention is acceptable for the current article directory layout.

=== Open Questions

* Should future validation require one summary file for every supported target?
* Should generated site or Markdown export tasks explicitly ignore `_summary_<target>.md` files?

=== Review Notes

Confirm that source-adjacent summaries should be committed as part of the
article source workflow before changing this ADR to accepted or reviewed.
