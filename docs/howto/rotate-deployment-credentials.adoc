= Rotate deployment credentials

Which credential the `Build Docs` workflow needs, how to renew it, and where to store it.
Why each credential exists is explained in the architecture documentation; this page only covers the steps.

== Overview

[cols="2,2,3,3,2", options="header"]
|===
| Secret | Stored in `dieterbaier/profile` as | What it is | Required access | Used by

| `PROFILE_REPO_TOKEN`
| Repository secret
| Fine-grained GitHub token
| Repository `dieterbaier/dieterbaier`, `Contents: Read and write`
| `deploy-github-readme`

| `ARTICLE_COMMENTS_REPO_TOKEN`
| Repository secret
| Fine-grained GitHub token
| Repository `dieterbaier/profile-artikelkommentare`, `Contents: Read and write`
| `deploy-site`

| `GITLAB_TOKEN`
| Repository secret
| GitLab personal access token
| Scope `write_repository` on `gitlab.com/brdietdidi/brdietdidi`
| `deploy-gitlab-readme`

| `SFTP_PASSWORD`
| Secret of the `production` environment
| Password of the SFTP user at Strato
| Write access to the configured remote base
| `deploy-site`, `deploy-architecture`
|===

The `SITE_*` secrets and the `SFTP_*` and `SITE_BASE_URL` variables are plain values in the `production` environment. They do not expire and only change when the value itself changes.
The `PREVIEW_SFTP_*` values in the deployment view belong to the preview target and do not exist yet.

== Which credential failed?

[cols="2,2,3", options="header"]
|===
| Job | Failing step | Renew

| `deploy-site`
| `Checkout article comments repository` or `Synchronize published article IDs`
| `ARTICLE_COMMENTS_REPO_TOKEN`

| `deploy-github-readme`
| `checkout github profile repo`, usually with `Bad credentials`
| `PROFILE_REPO_TOKEN`

| `deploy-gitlab-readme`
| `push readme to gitlab profile`
| `GITLAB_TOKEN`

| `deploy-site`, `deploy-architecture`
| `Deploy site to private webspace`, `Deploy architecture to private webspace`
| `SFTP_PASSWORD`, then the `SFTP_*` variables
|===

An expired `ARTICLE_COMMENTS_REPO_TOKEN` stops `deploy-site` before the upload, so the website is not deployed at all.
Reading and writing comments needs no token: the form is a GitHub issue form, and the list comes from the public GitHub API.
What the token keeps current is the allowlist of article IDs. Without it, comments on a newly published article do not get their article label.

== Renew a GitHub token

. Open https://github.com/settings/personal-access-tokens[Fine-grained personal access tokens]. The list shows each token's expiry date.
. Open the token and choose *Regenerate token*. This keeps repository and permissions. If the token no longer exists, create a new one with the access from the overview, and no further permissions.
. Copy the value and check it. The response must be `200` and name the new expiry date:
+
[source,sh]
----
curl -sI -H "Authorization: Bearer $(pbpaste)" \
  https://api.github.com/repos/dieterbaier/profile-artikelkommentare \
  | grep -iE '^HTTP|token-expiration'
----
+
For `PROFILE_REPO_TOKEN`, use the repository `dieterbaier/dieterbaier`. The check proves that the token is valid, not that it may push; `Check credentials` proves push permission.
. Store it, then <<verify,verify the credential>>:
+
[source,sh]
----
gh secret set ARTICLE_COMMENTS_REPO_TOKEN --repo dieterbaier/profile
----
+
`gh` asks for the value, which keeps it out of the shell history. In the browser, the same page is https://github.com/dieterbaier/profile/settings/secrets/actions[Actions secrets].

== Renew the GitLab token

. Open https://gitlab.com/-/user_settings/personal_access_tokens[Personal access tokens]. The list shows each token's expiry date.
. Rotate the token, or create a new one with the scope `write_repository`.
. Copy the value and check it. The command must print a commit hash:
+
[source,sh]
----
git ls-remote "https://oauth2:$(pbpaste)@gitlab.com/brdietdidi/brdietdidi.git" HEAD
----
. Store it, then <<verify,verify the credential>>:
+
[source,sh]
----
gh secret set GITLAB_TOKEN --repo dieterbaier/profile
----

== Change the SFTP password

The password does not expire on a schedule. If it changes at Strato, store the new value in the environment, not as a repository secret:

[source,sh]
----
gh secret set SFTP_PASSWORD --env production --repo dieterbaier/profile
----

In the browser, the same page is https://github.com/dieterbaier/profile/settings/environments[Environments], then `production`.

== Verify the credential

Run the `Check credentials` workflow. It checks every credential without deploying anything, and each credential has its own job:

[source,sh]
----
gh workflow run check-credentials.yml --repo dieterbaier/profile
gh run watch --repo dieterbaier/profile
----

Do not rely on a green `Build Docs` run after a push: a deployment job only runs when its paths changed, and a skipped job shows as green without having used the credential.

For the git targets, a green job proves that the token has push permission on the repository. It does not prove that a push to `main` passes branch rules, because the check pushes nothing. If you add a rule to `main` in a target repository, the next deployment that changes that target shows whether it still passes.

To deploy every target by hand, dispatch `Build Docs`. It runs every deployment job, whatever the last commit touched. A git target is only pushed when its content changed, so a green run does not prove the branch rules either:

[source,sh]
----
gh workflow run update-profile.yml --repo dieterbaier/profile --ref main
gh run watch --repo dieterbaier/profile
----

If a deployment failed because of the credential, re-run the failed job afterwards.

The check also runs every Monday and fails 14 days before a GitHub token expires. It cannot see the expiry of `GITLAB_TOKEN`, so add that date to your calendar, about two weeks ahead.
GitHub disables scheduled workflows after 60 days without repository activity. If the Monday runs stop, enable the workflow again under Actions.
